# CobbleMarket RP 外部签名码协议（网站 / 发卡网对接用）

本文档面向**已经有自己的充值网站（或使用发卡网）的服务器**：让你在自己的网站卖 RP，
玩家付款后拿到一个兑换码，在游戏内兑换。

设计目标是**网站与 MC 服务器零耦合** —— 不开端口、不做内网穿透、网站挂了不影响游戏。
服务器只做一件事：**验签**。任何能算 HMAC 的平台都能签码（PHP / Node / Python / Java 都行）。

> 玩家在**游戏内**兑换（RP 商城界面的「兑换 RP」入口，或 `/market points redeem <码>`）。
> 兑换成功后 RP 直接进余额，并写审计日志。

## 一、服务器要先打开这个功能

| 配置键 | 默认 | 说明 |
|---|---|---|
| `pointsExternalSecret` | `""` | HMAC 签名密钥，**建议 ≥32 字符随机串**。**留空 = 关闭外部码**（只接受游戏内生成的本地码） |
| `pointsExternalMaxDays` | `365` | 外部码的有效期上限（天）；签发跨度超过它的码一律拒绝 |

密钥必须与你的网站用的完全一致。

> ⚠⚠ **密钥只能放在服务端**（你的网站后端 / 本机），**绝不能**进客户端、进日志、进公开仓库。
> 它一旦进了前端页面 = 任何人都能自己签码 = **等于把印钞机交出去**。
> 服务器自己的日志也只记码前缀，不记全码（码 = 钱）。

## 二、码的形态

- 固定 **32 个 Crockford Base32 字符**，字符集为 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`
  （标准 Base32 去掉了易混淆的 **I / L / O / U**，防手抄歧义）
- 展示时按 4 位一组、共 **8 组**加连字符：`XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX`
- 玩家输入时可以带连字符、空格，也可以用小写 —— 服务器会归一化后再解析

## 三、二进制布局（20 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `version` | 固定 `0x01`；不认识的版本一律拒绝 |
| 1 | 6 | `serial` | 48 bit 随机数，**防重放**（同一个 serial 只能兑一次） |
| 7 | 4 | `amount` | 大端 int32，RP 面额，**必须 > 0** |
| 11 | 2 | `expiresDays` | 大端 uint16，**自 2026-01-01 UTC 起的天数**；`0` = 不过期 |
| 13 | 1 | `flags` | 固定 `0`（保留位） |
| 14 | 1 | `reserved` | 固定 `0`（保留位） |
| 15 | 5 | `signature` | **HMAC-SHA256(secret, 前 15 字节) 的前 5 字节** |

### 编码（20 字节 → 32 字符）

把字节流按**大端位序**每 5 bit 取一个值、查上面的字符表，**无 padding**（20 字节刚好 160 bit = 32 × 5 bit，不会有余数）。

### 签名要点

- 签名输入是 **payload 的原始 15 字节**，**不是** Base32 字符串、**不是**十六进制文本 ——
  避免不同实现因编码差异导致验签失败
- `secret` 按 **UTF-8** 转成字节再参与 HMAC
- 只取 HMAC 输出的**前 5 字节（40 bit）**：配合兑换节流与失败冷却，伪造不可行
- 本机生成 `serial` 时请用**密码学安全的随机源**（`SecureRandom` / `crypto.randomBytes` / `random_bytes` 等），
  别用 `Math.random()`：serial 撞车会让后一张码被当成"已用过"而失效

### `expiresDays` 怎么算

```
expiresDays = floor((签发时刻的 Unix 毫秒 + 有效天数 × 86400000) / 86400000) - 20454
```

`20454` 是 `2026-01-01T00:00:00Z` 的天数基准（`1767225600 / 86400`）。
不过期就写 `0`。**服务端按 UTC 当天 00:00 判定过期**，所以实际可用时间会比"签发时刻 + N 天"略短，属正常。

## 四、测试向量（自检用）

协议要能被第三方实现，必须能自检。用下面的固定输入，你算出来的码应当**逐字符相同**：

| secret | amount | expiresDays | serial (hex) | 期望的码 |
|---|---|---|---|---|
| `cobblemarket-test-vector-secret` | 100 | 0（不过期） | `0a1b2c3d4e5f` | `0451-PB1X-9SFG-0000-CG00-0000-D6R3-ZAYS` |
| `cobblemarket-test-vector-secret` | 500 | 0（不过期） | `ffffffffffff` | `07ZZ-ZZZZ-ZZZG-0001-YG00-0000-965D-EAQW` |

用本模组自带的签名器复现（Java 11+，单文件零依赖）：

```
java tools/SignPointCode.java cobblemarket-test-vector-secret 100 1 0 0a1b2c3d4e5f
```

> 向量只用 `expiresDays = 0`：带有效期的码其 `expiresDays` 依赖签发时刻，写不成固定期望值。
> 自检用 0 即可，其余字段与签名逻辑完全相同。

## 五、怎么签发

三种方式，按你的场景挑一种：

### 1. 服主自己签（最省事）

用本模组自带的签名器，在**本机**生成：

```
java tools/SignPointCode.java <secret> <面额> <数量> [有效天数] [serial十六进制]
```

例：

```
java tools/SignPointCode.java my-secret-key 100 5        # 5 张 100 点的码，不过期
java tools/SignPointCode.java my-secret-key 100 1 30     # 1 张、30 天有效
```

### 2. 发卡网

**预生成一批码上传给平台**，卖出后平台自动发货 —— **零开发**。
⚠ 预生成的码请带有效期（永久码的 serial 必须永久保留，会让服务器存档持续膨胀）。

### 3. 自建支付页（真正的"网页购买"）

在你的**支付回调**里调同一套签名逻辑（几十行），实时签发并展示给玩家。
你可以直接照抄 `tools/SignPointCode.java` 的 `sign` / `encode` / `format` 三个方法。

## 六、服务器侧的校验规则（实现时对齐）

服务器**按这个顺序**校验，任一不过即拒绝；**拒绝时不区分原因**（避免给爆破者反馈）：

1. 长度与 Base32 编码 —— 服务器容错：忽略连字符与空格、不区分大小写、`I` 与 `L` 按 `1` 处理、
   `O` 按 `0` 处理；`U` 不是合法字符（会被拒）
2. **签名**（先用常量时间比较验签，再谈其它）
3. `version` 是否为 `0x01`
4. `amount > 0`
5. 是否过期（**用服务端时间**，不信客户端）
6. 有效期跨度是否超过 `pointsExternalMaxDays`

**防重放**：验证通过后，服务器先把 `serial` 记入已用集合（并落盘），**再加余额** ——
崩溃窗口最坏是玩家少一次机会，绝不会重复发放。

## 七、与游戏内本地码的关系

两条路径**共用同一个兑换入口**（先试外部验签，再查本地码表），玩家不用区分：

| | 本地码（`/market points code create`） | 外部签名码 |
|---|---|---|
| 生成方 | 服主在**游戏内** | 服主在**游戏外**（签名器 / 网站 / 发卡网） |
| 服务器存不存 | 存表（含次数、绑定、有效期） | **不进表**，只记已用 serial |
| 典型用途 | 定向发放、活动码、补偿码 | **支付卖出、卡密** |
| 能不能作废/限次/绑定 | 都能 | 都不能 |

> 需要「限次 / 绑定某人 / 可作废」的码，请走**游戏内本地码**那条路。
> 外部码的特性是「服务器不需要认识它，也能验签」—— 这正是它能让你的网站与游戏零耦合的原因。
